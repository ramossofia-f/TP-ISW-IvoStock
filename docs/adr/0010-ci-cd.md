# ADR-0010: Integración y despliegue continuos con GitHub Actions

## Contexto y problema

La consigna exige integración continua y testing operativos desde la Entrega 2, y el ciclo de vida completo automatizado en la Entrega 3. El PRD compromete tests propios para los caminos de falla (RNF-12), un chequeo de que no haya credenciales en el repositorio (RNF-07) e imágenes construidas en CI (RNF-11). Hay que decidir dónde y cómo corre ese pipeline.

## Factores de decisión

* Que cada cambio a `main` pase por los mismos controles, sin depender de que alguien se acuerde.
* Build, tests, análisis estático y chequeo de secretos desde P0 (RNF-07, RNF-12).
* Imágenes reproducibles y despliegue efímero en M7, sin servicios pagos encendidos (RNF-11).
* Sin costo para un repositorio privado de tres personas.

## Opciones consideradas

* **Opción A**: GitHub Actions, con el pipeline versionado en el repositorio.
* **Opción B**: Otro servicio de CI externo (por ejemplo GitLab CI o CircleCI).
* **Opción C**: Build, tests y despliegue manuales.

## Decisión

Opción elegida: "Opción A: GitHub Actions", porque el repositorio ya está en GitHub y compartido con la cátedra, y la capa gratuita alcanza para el volumen de la cursada.

* **En cada push y pull request:** instalación de dependencias desde el archivo del proyecto, ruff, pytest (incluidos los caminos de falla a medida que se implementan) y un escáner de secretos.
* **Desde M7:** construcción de las imágenes de cada servicio, publicadas en el registro de GitHub con la revisión como etiqueta, y despliegue efímero con configuración externa.
* Una rama no se mergea a `main` si el pipeline falla.

### Consecuencias

* A favor, porque cada revisión de `main` queda asociada a un resultado verificable, que es lo que la cátedra corrige.
* A favor, porque no hay servicios ni cuentas extra que mantener.
* En contra, porque el pipeline consume minutos de la capa gratuita y hay que mantenerlo.
* Neutral, porque cambiar de proveedor de CI implica reescribir el archivo del pipeline, pero no el código del sistema.

### Confirmación

* Un test que falla a propósito bloquea el merge.
* Un secreto ficticio en una rama de prueba hace fallar el escáner.
* En M7, la imagen desplegada corresponde a la revisión que pasó el pipeline.

## Ventajas y desventajas de las opciones

### Opción A: GitHub Actions

* A favor, porque está integrado con el repositorio y los pull requests que ya usa el equipo.
* En contra, porque ata el pipeline a GitHub.

### Opción B: Otro CI externo

* A favor, porque algunos ofrecen más minutos o funciones específicas.
* En contra, porque suma una cuenta y una integración más, sin una ventaja que este proyecto necesite.

### Opción C: Manual

* A favor, porque no requiere configuración inicial.
* En contra, porque permite saltear controles y hace difícil reproducir el estado de una entrega.
